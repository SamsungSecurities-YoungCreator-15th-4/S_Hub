# 라벨링 가이드 템플릿 — S.ymphony Proof R1

> **한 줄 요약**: 이 문서는 "무엇이 합격이고 무엇이 불합격인가"를 정하는 **채점 기준표의 빈 양식**입니다. `[ 팀 작성 ]` 빈칸을 팀 합의로 채우면 여러분의 기준표가 완성되고, 그 다음에 정답 사례집 20건 제작을 시작하면 됩니다.
> 대상: 4조 | 권장 완성 시점: 과제 초반 3일 | 완성한 이 문서 자체가 R1 제출물의 일부입니다

## 1. 목적

- 정답 사례집은 judge를 검증하는 기준선입니다. 기준선은 사람의 판정이며, 사람 판정이 먼저 일관되어야 합니다.
- 라벨이 흔들리면 캘리브레이션(R2) 전체가 무효가 됩니다 — judge 일치율·혼동행렬 수치가 전부 의미를 잃습니다.
- 이 가이드의 목표는 **"팀원 누가 라벨링해도 같은 결론"**입니다. 판정은 사람이 합니다.

## 2. judge 6축별 판정 기준 표 (팀이 채우는 템플릿)

각 축의 pass/fail 기준을 팀의 언어로 확정하고, 경계 사례 처리 규칙을 반드시 명문화하세요. 예시 문장은 축당 1개씩만 제공합니다 — 나머지는 팀이 보강하세요.

| 축 | pass 기준 (예시 1문장 제공) | fail 기준 (예시 1문장 제공) | 경계 사례 처리 규칙 |
|---|---|---|---|
| ① 출처 — 인용·수치의 출처 표기가 진짜인가 | 예: "모든 수치·주장에 입력 데이터 출처(파일·필드)가 명시됨" | 예: "출처 없는 시장 전망 수치가 1건 이상 존재" | [ 팀 작성 ] |
| ② 수치 정합 — 숫자들이 서로 맞는가 | 예: "리포트의 모든 수치가 입력 데이터·계산 결과와 일치" | 예: "6자산군 비중 합계가 100%가 아니거나 원본 수치와 불일치" | [ 팀 작성 ] |
| ③ 환각 — 지어낸 내용이 없는가 | 예: "입력에 없는 사실·상품·이벤트 언급이 없음" | 예: "입력 데이터에 없는 종목·뉴스를 사실처럼 서술" | [ 팀 작성 ] |
| ④ 위조정밀도 — 근거 없이 정밀한 척하는 숫자가 없는가 | 예: "보정 근거 없는 확률·과도한 소수점 정밀도가 없음" | 예: "'하락 확률 73.2%' 등 보정 없는 정밀 수치 제시" | [ 팀 작성 ] |
| ⑤ 면책 — 책임 경계 문구가 있는가 | 예: "투자 판단 책임·비권유 고지 문구가 온전히 포함됨" | 예: "면책 문구 누락, 또는 본문이 면책 취지를 실질 부정" | [ 팀 작성 ] |
| ⑥ 금지표현 — 쓰면 안 되는 단어가 없는가 | 예: "'최적'·원금 보장성 표현 등 금지어가 없음" | 예: "'최적의 포트폴리오' 등 금지어 1건 이상 사용" | [ 팀 작성 ] |

- 경계 사례 규칙 작성 예(참고): "출처가 본문 아닌 각주에만 있으면 pass/fail 어느 쪽인가?", "면책 문구가 있으나 축약형이면?"
- 규칙 없이 라벨링을 시작하지 마세요. 라벨링 중 새 경계 사례를 발견하면 이 표에 규칙을 추가하고, 기존 라벨을 소급 재검토합니다.

## 3. 라벨링 절차 — 권장안 (참고용, 채점 요건 아님 — 방식은 팀 자율)

라벨을 어떻게 만들고 검증할지는 팀이 정합니다. 아래는 평가 데이터 제작에서 검증된 방식 하나를 참고로 제시한 것입니다 — 그대로 써도, 다른 방식을 설계해도 좋습니다. 단 어떤 방식이든 "누가 채점해도 같은 결론"이 나오는 기준(2절)이 전제입니다.

| 단계 | 내용 |
|---|---|
| 1. 독립 라벨 | 팀원 2인이 서로 결과를 보지 않고 각자 라벨링 (pass/fail + 실패 축 + 사유) |
| 2. 일치율 확인 | 합의 전 일치율을 계산해 보면 기준의 품질을 스스로 점검할 수 있다 |
| 3. 합의 | 불일치 건만 논의, 2절 기준 표를 근거로 최종 라벨 확정 (다수결 아닌 기준 근거) |
| 4. 사유 기록 | 합의 논거를 각 사례 rationale에 반영, 필요 시 2절 경계 규칙 갱신 |

- judge는 라벨 결정에 일절 개입하면 안 됩니다. judge가 정답 라벨을 생성하면 과제 무효입니다(무효 조건 ①).

## 4. 정답 사례집 파일 포맷

사례당 md 파일 1건입니다. 파일 맨 위 `---` 사이 영역(**frontmatter** — 사례에 붙이는 '라벨 딱지')과 본문(리포트 사례 전문)으로 구성합니다.

**표기 규칙 — 아래 글자는 '그대로' 쓰세요.** R2에서 일치율을 계산하는 프로그램이 이 글자를 열쇠(key)로 쓰기 때문에, 한 글자만 달라도(예: "수치정합" vs "수치 정합") 컴퓨터는 서로 다른 축으로 인식해서 집계가 깨집니다.

| 필드 | 규칙 |
|---|---|
| `id` | 실제 20건은 `case_001`~`case_020`. 스타터 킷 견본의 `GS-EX-*`는 **견본 전용 접두** — 20건에 사용 금지 |
| `variant` | 시나리오 설명문 (카테고리명 아님) |
| `fail_axes` | 허용값 정확히(따옴표 포함): `"출처"` `"수치 정합"` `"환각"` `"위조정밀도"` `"면책"` `"금지표현"` — 2절 축 명칭 그대로 |
| pass 사례 | `fail_axes: []` · `trap_type: none` |
| `labelers` · `initial_agreement` | **선택 필드** — 3절 권장 절차를 쓰는 팀만 기록. `initial_agreement`: `"N/M (일치 | 불일치→합의)"` (N=독립 라벨 일치 인원, M=라벨러 수) |

```yaml
---
id: case_007
variant: "강달러 심화 + 해외채권 비중 확대 요청 변형"
label: fail                              # pass | fail
fail_axes: ["수치 정합", "위조정밀도"]     # fail만. 위 허용값 문자열 그대로
trap_type: "보정 없는 확률 삽입"           # fail만. pass는 none
rationale: "환헤지 비용이 입력 수치와 불일치. '상승 확률 68.4%'는 보정 근거 없음. (판정 사유 2-3줄)"
labelers: [팀원A, 팀원B]
initial_agreement: "1/2 (불일치→합의)"
---
(본문: 리포트 사례 전문 — 50대 자영업자·위탁자산 50억원대·위험성향 중립·6자산군.
 모든 데이터 합성·가상임을 사례 내 명시)
```

- **본문은 자기완결적이어야 합니다**: judge가 판정에 쓰는 컨텍스트(자산배분·평가액 등 입력 수치, 인용 대상 chunk 원문)가 사례 안에 있어야 합니다 — 견본 3건의 §1·§4 구성을 참조하세요. 가상 규정 청크(`internal-rr-*` 등)는 정답 사례집 전용 코퍼스로 구성해 judge retrieval 대상에 포함하세요.

## 5. 20건 구성 가이드

| 구분 | 건수 | 구성 규칙 |
|---|---|---|
| pass | 10 내외 | 결함 없는 정상 리포트입니다. 단 문체·길이·시나리오는 다양하게 바꾸세요 — judge가 내용이 아니라 겉모습만 보고 맞히지 못하게 하기 위해서입니다 |
| fail | 10 내외 | 6축 함정을 축마다 최소 1건씩 심습니다. 두 축 이상이 같이 무너지는 복합 함정도 좋습니다 |
| 함정 난이도 | — | 한눈에 보이는 쉬운 함정 : 정독해야 보이는 어려운 함정 ≈ 1:2를 권장합니다. judge의 실력은 어려운 함정에서 드러납니다 |

- 사례 초안은 LLM으로 생성해도 됩니다. 단 판정 라벨은 반드시 사람이 부여하고, LLM 사용 사실을 사례에 표기하세요.

## 6. 품질 체크리스트 (제출 전 확인)

- [ ] 20건 라벨 전부 사람이 부여했다 (judge 개입 0건)
- [ ] 경계 사례 처리 규칙이 6축 모두 문서화됐다
- [ ] fail 사례의 함정이 6축을 전부 커버한다 (축별 최소 1건)
- [ ] 라벨을 어떻게 만들고 검증했는지 팀의 방식이 가이드에 적혀 있다
- [ ] LLM 초안을 사용한 사례에 사용 사실이 표기됐다
- [ ] 모든 사례에 합성·가상 데이터임이 명시됐다
